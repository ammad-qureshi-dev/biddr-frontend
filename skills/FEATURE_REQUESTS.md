# App Feature Requests

- [FEATURE ADDED @ 2026-08-24] on the account page, show if that account is verified. On the eyebrow="Account" in ./app/account.tsx, add a badge signalling if it has been verified. For a non-verified account, make the badge say "Not Verified". When the user hovers over it, make a tip (default system tip) show up saying "Account is not verified, please verify". On a verified account, just show a green checkmark. When the user hovers over the checkmark, show a tip saying "Account is verified"
- [FEATURE ADDED @ 2026-08-24] when an account is already verified, don't show the "Verify your account" section, since it won't be needed
- [FEATURE ADDED @ 2026-10-10] add a "Pickup information" section for an auction's location (backend added `pickupLocation` to Auction in catalog-service as JSON: unit, street, city, postalCode, state, country — all required). Shown on the auction page, editable on the create/edit forms, and summarized as "City, State" on browse cards, the My Auctions table, and the item page.
- [BLOCKED — needs backend @ 2026-10-10] **Wishlist** — let a signed-in user save auctions/items to come back to. Frontend plan: a secondary "Watch" button (bookmark icon) on the auction page and item page, a filled/unfilled state, and a "Wishlist" page in the sidebar Workspace section listing saved items with their status, current bid, and countdown. Needs from the backend: an endpoint to add, remove, and list a user's wishlist (keyed by the `X-App-User-Id` the gateway injects), plus a way to tell whether a given item is already wishlisted. Nothing exists for this in any service today. Open question: wishlist **items** or whole **auctions**? Items fits bidding better (you watch the Rolex, not the whole estate sale); auctions is simpler.
- [BLOCKED — needs backend @ 2026-10-10] **View count per item** — show how many times an item has been viewed (e.g. "1,240 views" on the item page, optionally on auction item rows). Frontend plan: record a view when the item page loads, then display the count in the item details. Needs from the backend: a view counter on the item (catalog-service) with an endpoint to record a view and the count returned on `ItemResponse`. Nothing exists today. Open questions before building: total views or unique viewers? Should the owner's own views and repeated refreshes count? Counting every page load inflates numbers fast; unique-per-user-per-day is a common middle ground.
- [BLOCKED — needs backend @ 2026-10-10] **Payment** — let the winning bidder pay for an item they won. Frontend plan: a "Pay now" action on won items (My Bids → Won, and the item page for the winner), a payment status on the auction owner's view, and the 3-day payment deadline shown as a countdown. Needs from the backend: the `payments` service currently has only `PaymentProcessingRequest` (requestId, itemId, ownerId, accepted, requestExpiry = 3 days, expiring 23:59 that day) and no controller, no API-gateway route, and no payment-provider integration, so there is nothing to call yet. Also note `ItemResponse.priceSoldAt` is never set server-side, so the amount owed would have to come from the winning (`WINNER`) bid. Open questions: which provider (e.g. Stripe Checkout keeps card data off our servers), what happens when the 3-day window expires (offer to the next-highest bidder?), and whether "accepted" means the owner accepted the payment or the buyer accepted the request.
